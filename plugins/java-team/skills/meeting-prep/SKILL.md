# 개발3팀 자바 회의 준비

## 무엇을 하는 스킬인가

Confluence 회의 페이지의 `## 업무 공유` > `### <본인 이름>` 아래에 들어갈 내용을 만들어 반영한다.

혼자 초안을 쓰는 도구가 아니다. **수집 → 사용자 선택 → 정리 → 사용자 검토 → 반영**의 순서를 지키는 것이 이 스킬의 전부다. 각 단계에서 사용자의 확인 없이 다음으로 넘어가지 않는다.

## 배경 — 회의가 두 번인 이유

자바 회의는 월요일·수요일에 열린다(금요일 회의는 필요할 때만).

- **월요일(온라인)** 은 짧은 공유 시간이다. 이번 주에 무엇을 하고 있는지 굵직하게만 말한다.
- **수요일(오프라인)** 은 주간 업무 리뷰 시간이다. 발표자 PC를 화면에 연결해 한 사람당 10~20분 동안 한 일을 자세히 보여준다.
- 두 회의는 이어진다. **월요일에 공유했다고 수요일 공유에서 빠지면 안 된다.** 월요일에 말한 일은 수요일에 진행 결과까지 붙여 다시 다룬다.
- 그래서 이 스킬은 월요일엔 굵직하게 뽑고, 화~수요일에 다시 실행하면 월요일 공유 내용과 그 이후 작업을 함께 모아 **무엇을 중점으로 다룰지 사용자와 함께 정한다.**

## 회의 형식

| | 월요일 — 간단 공유 | 수요일 — 주간 업무 리뷰 |
| --- | --- | --- |
| 실행 시점 | 월요일 | **화요일 오후 ~ 수요일** |
| 목적 | 진행 상황을 짧게 공유 | 한 주 동안 한 일을 자세히 리뷰 |
| 항목 | 최상위 항목 **5개**, **하위 항목 없음** | 최상위 항목 최대 5개, 필요하면 하위 항목 포함 |
| 수집 범위 | 직전 회의 이후 | **직전 수요일 회의 이후** + 이번 주 월요일에 공유한 내용 |
| 정하는 것 | 굵직한 일 5개 | 월요일 공유분 + 이후 작업 중 **무엇을 중점으로 다룰지** |
| 분량 | 항목당 약 2분 | 항목당 약 2분, 인당 10~20분 안에 끝나는 분량 |
| 시각화 | 쓰지 않음 | 필요하면 표·다이어그램 ([6단계](#6-시각화-검토-수요일)) |

## 절대 하지 말 것

- **다른 팀원이 작성한 영역을 추가·수정·삭제하지 않는다.** 본인 `### 이름` 섹션 외에는 한 글자도 건드리지 않는다. 페이지 상단의 안건, `## 설치 & 교육`, `## 리서치 공유`, `## 주요 공유`, `# 참고` 도 마찬가지다.
- **최상위 항목은 최대 5개.** 넘으면 사용자에게 무엇을 뺄지 묻는다. 임의로 자르지 않는다.
- **수요일 준비에서 월요일 공유 항목을 빼지 않는다.** 5개가 넘으면 빼는 대신 관련 항목끼리 묶는 안을 제시한다.
- **사용자가 담당한 영역이나 작업을 추측으로 적지 않는다.** 근거가 없으면 묻는다. 진행 상태도 마찬가지다 — 확실하지 않으면 묻고 확정한다.
- **페이지 본문에 지라 티켓 번호를 쓰지 않는다.** 대신 진행 상태를 붙인다 ([4단계](#4-결과--과정으로-정리)).
- **검토받지 않은 내용을 Confluence에 올리지 않는다.** 사용자가 명시적으로 승인한 상태에서만 반영한다.

## 절차

### 0. 팀 설정 불러오기

회의 페이지 위치와 업무 공유 채널은 팀마다 다르므로 스킬에 적어 두지 않는다. 처음 실행할 때 사용자에게 받아 저장하고, 다음부터는 저장된 값을 쓴다.

설정 파일: `${CLAUDE_PLUGIN_DATA}/meeting-prep.json` — 플러그인을 업데이트해도 유지되고, 플러그인을 지우면 함께 지워진다.

```json
{
  "confluence": {
    "meetingRootPageId": "<회의 페이지들의 최상위 페이지 ID>",
    "meetingRootTitle": "<그 페이지 제목>"
  },
  "slack": {
    "workShareChannelId": "<채널 ID>",
    "workShareChannelName": "<채널 이름>"
  },
  "jira": {
    "browseBaseUrl": "<https://<사이트>/browse>"
  },
  "savedAt": "YYYY-MM-DD"
}
```

**파일이 있으면** 읽어서 쓴다. 매번 확인받지 않는다.

**파일이 없거나 값이 비어 있으면** 처음 실행이다. 필요한 값만 묻는다.

1. **Confluence** — "최근 회의 페이지(`YYYY/MM/DD : N주차`) 링크를 하나 알려주세요."
   - 링크의 페이지를 읽어 회의 페이지가 맞는지(제목 형식, `## 업무 공유` 섹션) 확인한다.
   - 그 페이지의 상위(월별 `스크럼 YYYY-MM` 페이지)의 상위가 회의 페이지들의 최상위 페이지다. 그 ID와 제목을 저장한다. 구조가 다르면 추측하지 말고 어느 페이지 아래에서 찾으면 되는지 사용자에게 묻는다.
2. **Slack** — Slack 커넥터가 있을 때만 묻는다. "업무 공유 댓글을 다는 Slack 채널 이름(또는 링크)을 알려주세요. 쓰지 않으면 건너뛰어도 됩니다."
   - 채널을 조회해 ID를 확인하고 이름과 함께 저장한다.
   - 사용자가 건너뛰면 `slack` 을 `null` 로 저장하고, 이후 Slack 수집을 건너뛴다.
3. **Jira** — 묻지 않는다. Atlassian 커넥터로 접근 가능한 사이트 주소를 확인해 `https://<사이트>/browse` 를 저장한다. 4단계에서 상태 텍스트에 티켓 링크를 걸 때 쓴다.
   - 사이트가 여러 개면 어느 사이트의 티켓을 쓰는지 한 번 묻는다.
   - Atlassian 커넥터가 없으면 `jira` 를 `null` 로 저장하고, 링크 없이 상태 텍스트만 쓴다.

저장한 뒤 한 줄로 알린다.

> "회의 페이지 위치와 업무 공유 채널을 저장했습니다. 다음부터는 묻지 않습니다. 바꾸려면 '회의 설정 다시 해줘'라고 말해주세요."

**저장된 값이 맞지 않으면**(페이지가 없어졌거나 검색 결과가 0건, 채널을 읽을 수 없음) 그 값만 다시 묻고 덮어쓴다. 사용자가 설정을 바꾸자고 하면 같은 질문을 다시 한다.

### 1. 회의와 수집 범위 확인

**지금 요일과 시간으로 어느 회의를 준비하는지 정한다.** 추측하지 말고 현재 시각을 확인한다.

```bash
date '+%u %H:%M %Y-%m-%d'   # %u: 1=월 … 7=일
```

| 실행 시점 | 모드 |
| --- | --- |
| 월요일 | **월요일 간단 공유** |
| 화요일 12:00 이후 ~ 수요일 | **수요일 주간 리뷰** |
| 그 밖(화요일 오전, 목·금·주말) | 어느 쪽으로 준비할지 사용자에게 묻는다 |

정한 모드를 한 줄로 알리고 다르면 바꿀 수 있게 한다.

> "화요일 오후라서 수요일 주간 리뷰용으로 준비합니다. 지난 수요일(10/15) 이후 작업과 이번 주 월요일 공유 내용을 모읍니다."

**수집 시작 날짜**를 정한다. Confluence에서 최근 회의 페이지를 찾아 날짜를 파악한다.

회의 페이지 제목은 `YYYY/MM/DD : N주차` 형식이고, 월별 상위 페이지(`스크럼 YYYY-MM`) 아래에 있다. 0단계에서 저장한 최상위 페이지 아래를 찾는다.

```
ancestor = <meetingRootPageId> AND type = page ORDER BY created DESC
```

- 월요일 모드: **직전 회의** 페이지의 날짜부터. 그 페이지를 찾아 둔다(2단계에서 본인 섹션을 읽어 대조한다)
- 수요일 모드: **직전 수요일 회의** 페이지의 날짜부터. 이번 주 월요일 회의 페이지도 함께 찾아 둔다(2단계에서 읽는다)

날짜가 다르면 사용자가 말한 날짜를 쓴다.

### 2. 작업 내역 수집

수집 시작 날짜를 기준으로 모은다. 사용 가능한 소스만 쓰고, 없으면 건너뛴다. 건너뛴 소스는 리스트 아래에 한 줄로 알린다.

**Jira** — Atlassian 커넥터로 본인이 담당한 티켓의 상태 변화, 코멘트, 완료 건을 조회한다.

티켓이 한꺼번에 갱신되는 날이 있다 — 스프린트 정리, 릴리즈 전 상태 점검처럼 **실제 작업과 상관없이 상태만 건드린 것들**이다. 그런 묶음이 커 보이면 임의로 버리지 말고 **한 줄로 묶어 보여주고 사용자에게 확인한다.**

> "10/26 에 상태만 갱신된 티켓이 14건 있습니다. 티켓 정리 작업으로 보이는데, 공유 후보에서 빼도 될까요?"

**Confluence** — 수집 범위 안에 본인이 만들거나 고친 문서를 찾는다. 회의 페이지 자체는 제외한다.

```
type in (page, blogpost) AND contributor = currentUser() AND lastmodified >= "<수집 시작 날짜>"
  AND NOT ancestor = <meetingRootPageId> ORDER BY lastmodified DESC
```

설계 문서, 리서치 정리, 장애 분석처럼 코드로 남지 않는 작업을 찾는 데 쓴다. 같은 작업이 Jira·GitHub에도 있으면 하나로 합친다.

**GitHub**

```bash
git log --since="<수집 시작 날짜>" --author="$(git config user.email)" --oneline
gh pr list --author "@me" --state all --search "updated:><수집 시작 날짜>"
gh pr list --author "@me" --state merged --search "merged:><수집 시작 날짜>"
gh issue list --author "@me" --state all --search "created:><수집 시작 날짜>"
gh issue list --assignee "@me" --state all --search "updated:><수집 시작 날짜>"
```

이슈는 **등록한 것과 담당으로 잡힌 것을 모두** 가져온다. 작성한 코드가 없어도 이슈를 열어 문제를 드러낸 것 자체가 공유할 만한 작업이다. 두 조회에 같은 이슈가 걸리면 하나로 합친다.

**Slack 업무공유 댓글** — Slack 커넥터가 있으면 읽는다.

- 0단계에서 저장한 업무 공유 채널만 읽는다. 저장된 채널이 없으면 이 소스를 건너뛴다. 채널 이름을 추측해서 다른 채널을 읽지 않는다.
- 그 채널에는 매일 아침 워크플로우가 업무 공유 요청 메시지를 올리고, 팀원들이 그 스레드에 댓글로 그날 업무를 적는다.
- 수집 범위 안의 업무 공유 요청 메시지마다 스레드를 열어 **본인이 단 댓글만** 가져온다. 다른 팀원의 댓글은 읽지 않는다.
- 댓글은 Jira·GitHub에 남지 않은 작업(회의, 리서치, 고객 대응, 문서 작업 등)을 찾는 데 특히 쓸모 있다. 같은 작업이 Jira·GitHub에도 있으면 하나로 합친다.

**지난 회의에 공유한 내용 (두 모드 모두)** — 회의 페이지의 `## 업무 공유` 아래 본인 섹션을 읽는다. 어느 페이지를 읽는지는 모드마다 다르다.

| 모드 | 읽는 페이지 |
| --- | --- |
| 월요일 | **직전 회의** (보통 지난 수요일. 금요일 회의가 있었으면 그 페이지) |
| 수요일 | **이번 주 월요일** |

페이지가 없거나 본인 섹션이 비어 있으면 그렇다고 알리고 넘어간다.

읽은 항목을 이번에 모은 것과 **하나씩 대조해** 셋 중 하나로 표시한다.

| 대조 결과 | 표시 | 어떻게 하나 |
| --- | --- | --- |
| **상태가 바뀜** (진행 중 → 완료 등) | `→ 이후: …` | 공유할 값이 있다. 후보로 올린다 |
| **변화 없음** | `→ 이후: 변화 없음` | 월요일 모드는 기본으로 빼고 뺐다는 것을 한 줄로 알린다. 수요일 모드는 뺄 수 없다 (월요일 공유분은 빼지 않는다) |
| **어긋남** | `→ 확인 필요` | **사용자에게 묻고 정한다.** 추측해서 맞추지 않는다 |

어긋남은 이런 경우다 — 지난 회의엔 있는데 이번 범위의 어느 소스에도 흔적이 없다, 지난 회의엔 `(완료)` 인데 이번에 또 손댄 기록이 있다, 같은 일인지 다른 일인지 판단이 안 선다.

> "지난 회의에 `워크스페이스 접근 기록` 을 (진행 중)으로 공유했는데 이번 범위에는 흔적이 없습니다. 끝난 일인가요, 아직 그대로인가요?"

모은 것을 **번호를 붙여 그대로 리스트업해서 보여준다.** 이 단계에서는 해석하거나 요약하지 않는다. 사용자가 무엇이 있었는지 한눈에 보는 것이 목적이다.

```
지난 수요일(10/15) 이후 확인된 작업입니다.

지난 회의(10/20)에 공유한 항목 — 대조 결과
P1. 워크스페이스 접근 기록이 남게 됨 (진행 중)
    → 이후: PR #482 머지, 티켓 완료 → (완료)로 바뀜
P2. 알림 문구가 사용자 언어 설정을 따르게 됨 (완료)
    → 이후: 변화 없음
P3. 스토리지 연동 방식 비교 (진행 중)
    → 확인 필요: 이번 범위의 어느 소스에도 흔적이 없음

Jira
1. AIP-1234 Workspace 접근제어 로그 — 진행 중
2. AIP-1240 알림 템플릿 로케일 수정 — 완료

GitHub PR
3. PR #482 feat: add workspace access audit log — merged
4. PR #485 fix: notification locale fallback — open

GitHub Issue
5. Issue #77 Harbor 이미지 pull 간헐 실패 — 등록함, open

커밋
6. 커밋 7건 (feature/access-log 브랜치)

Confluence
7. 스토리지 연동 방식 비교 (10/17 작성)

Slack 업무공유 댓글
8. 10/16 고객사 설치 사전 점검 회의 참석
9. 10/17 경쟁사 스토리지 연동 방식 리서치
```

`P` 묶음은 두 모드 모두에 나온다. 월요일 모드에서 `변화 없음` 인 항목은 리스트 아래에 **"지난 회의와 같아서 뺀 항목"으로 한 줄만 적고** 선택지에는 올리지 않는다.

### 3. 공유할 항목 선택

리스트를 보여준 뒤 **다중 선택 프롬프트**로 사용자가 회의에 공유할 것을 고르게 한다. 대화로 묻지 말고 선택 UI를 쓴다.

선택하지 않은 항목은 그대로 버린다. 왜 뺐는지 묻지 않는다.

#### 선택지로 묶는 법

**선택 UI 는 한 번에 최대 16개(질문 4개 × 선택지 4개)까지 띄울 수 있다.** 2단계 리스트는 보통 그보다 길다. 아래 순서로 묶어 16개 안에 넣는다. 묶는 기준을 매번 새로 짜지 않는다.

1. **같은 티켓에 달린 것끼리 묶는다.** 티켓 하나와 그 티켓의 PR·커밋은 한 선택지다.
2. **한 변경이 여러 repo 에 걸쳐 있으면 한 묶음이다.** 티켓 키가 같거나 제목이 같은 PR 은 repo 가 달라도 함께 묶는다 (백엔드 + 프론트 + 설치 도구처럼).
3. **티켓 없는 커밋·Confluence 문서·Slack 댓글은 가장 가까운 묶음에 붙인다.** 붙일 데가 없으면 그것만으로 한 선택지가 된다.
4. **`P` 항목(지난 회의 공유분)은 묶지 않는다.** 상태가 바뀐 것은 그대로 한 선택지다.

**묶음 이름은 결과로 짓는다** — 제품이 어떻게 달라지는지. 커밋 제목이나 티켓 요약을 옮겨 적지 않는다. 선택지 설명에는 근거(티켓 키, PR 번호, Slack 날짜)를 적어 사용자가 무엇인지 알아볼 수 있게 한다.

**묶고도 16개를 넘으면** 굵직한 순으로 16개만 올린다. 순서는 ① 완료된 것 ② 제품이 달라지는 것 ③ 티켓이 있는 것이다. 그리고 **몇 개를 뺐는지 한 줄로 알리고, 번호로 더 넣을 수 있다고 덧붙인다.** 뺀 것은 2단계 리스트에 번호로 이미 떠 있다.

> "28건을 11개로 묶었습니다. 4건은 선택지에서 뺐는데, 넣을 게 있으면 리스트 번호로 말해주세요."

선택 UI 를 쓸 수 없는 환경이면 리스트 번호로 받는다.

**월요일 모드** — 굵직한 것만 고르게 한다. 작은 수정이나 같은 일의 커밋들은 하나로 묶어 제시한다. 상태가 바뀐 `P` 항목은 선택지에 넣고, `변화 없음` 인 `P` 항목은 넣지 않는다.

**수요일 모드** — 월요일 공유 항목(`P`)은 이미 포함된 것으로 두고, 그 밖에서 더할 것만 고르게 한다. 고른 뒤 **무엇을 중점으로 다룰지 함께 정한다.**

1. 포함된 항목 전체(월요일 공유분 + 새로 고른 것)를 보여주고, 관련된 것끼리 묶는 안을 제시한다. 월요일 항목에 이어지는 작업은 그 항목 아래로 붙인다.
2. **중점 항목**을 고르게 한다(선택 UI). 중점 항목은 하위 항목으로 과정까지 자세히 쓰고, 6단계 시각화 후보가 된다. 나머지는 한 줄 위주로 짧게 쓴다.
3. 인당 10~20분에 맞는지 어림해서 알려준다. 넘치면 중점을 줄이거나 짧게 쓸 항목을 정하자고 제안한다.

> "월요일에 말한 2건과 새 작업 3건, 모두 5건입니다. 이 중 자세히 리뷰할 것을 골라주세요. 2건 정도면 15분 안팎입니다."

### 4. 결과 → 과정으로 정리

**번호 목록으로 쓴다.** 불릿(`-`)을 쓰지 않는다.

| 층 | 내용 | 월요일 | 수요일 |
| --- | --- | --- | --- |
| **최상위 항목** | 이 작업이 프로덕트에 어떤 영향을 주는가 — **결과** | 5개 | 최대 5개 |
| **하위 항목** | 그 결과를 위해 무엇을 했는가 — **과정** | 쓰지 않음 | 항목당 3개 이내, 필요할 때만 |

최상위 항목은 제품이 어떻게 달라지는지를 쓴다. 커밋 제목을 옮겨 적는 자리가 아니다.

**월요일** — 굵직하게, 한 줄로 끝낸다. 과정이 꼭 필요하면 같은 줄 끝 괄호 안에 짧게 붙인다.

```markdown
1. 워크스페이스를 누가 언제 열고 닫았는지 기록이 남게 됨 (진행 중)
2. 알림 문구가 사용자 언어 설정을 따르게 됨 (완료)
3. 알림을 사용자마다 켜고 끌 수 있게 할 예정
```

**수요일** — 다른 팀원이 읽어도, AIPub을 사려는 고객이 읽어도 이해되도록 쓴다. 중점 항목은 과정을 하위 항목으로 내리고, 나머지는 한 줄 위주로 쓴다. 월요일에 공유한 항목은 그 뒤 달라진 점(완료, 머지, 새로 알게 된 것)을 반영해 고쳐 쓴다.

```markdown
1. 워크스페이스를 누가 언제 열고 닫았는지 기록이 남게 됨 (완료)
    1. 접근 제어 지점에 감사 로그 추가
    2. 로그 보관 기간은 기본 90일로 설정
```

#### 진행 상태를 붙인다 — 티켓 번호는 쓰지 않는다

읽는 사람이 **끝난 일인지, 하는 중인지, 아직 안 한 일인지**를 한눈에 알 수 있어야 한다. 최상위 항목 줄 끝 괄호에 상태를 쓴다. 세 가지만 쓴다.

| 상태 | 쓰는 때 |
| --- | --- |
| **(완료)** | 머지됐거나 티켓이 완료됨. 더 할 일이 남아 있지 않음 |
| **(진행 중)** | 손대고 있음 — 작성 중, 리뷰 중, PR 올려 둔 상태, 티켓이 진행 중 |
| **(할 예정)** | 아직 시작하지 않았고 이번 주/다음에 할 일 |

- 한 항목 안에서 상태가 갈리면 **덜 끝난 쪽**을 쓰고, 어디가 남았는지 괄호 안에 덧붙인다 — `(진행 중, 화면 쪽만 리뷰 중)`.
- 과정 메모를 괄호에 같이 넣을 때는 **상태를 맨 뒤에** 둔다 — `(디자이너 리뷰 반영, 완료)`.
- 수요일에 하위 항목까지 쓸 때는 **최상위 항목에만** 붙인다. 하위 항목마다 상태가 다를 때만 그 줄에 붙인다.
- **상태가 확실하지 않으면 사용자에게 묻고 확정한다.** 추측해서 "완료"라고 쓰지 않는다. 티켓이 열려 있는데 PR 은 머지됐다거나, 근거가 Slack 댓글뿐이라 어디까지 간 일인지 모를 때가 여기 해당한다. **답을 받기 전에는 그 항목의 상태를 비워 둔다.**

  > "`백엔드 wiki` 는 지금 어디까지 왔나요? 완료 / 진행 중 / 할 예정 중에 골라주세요."

- "할 예정"은 문장으로 녹여 써도 된다 — `… 할 예정`.

**상태 텍스트에 그 작업의 지라 티켓을 링크로 건다.** 번호는 안 보이면서 티켓으로 바로 갈 수 있다. 0단계에서 저장한 `jira.browseBaseUrl` 에 티켓 키를 붙여 쓴다.

```markdown
… 백오피스에서 바로 확인할 수 있게 됨 ([완료](https://<사이트>/browse/AIP-3212))
… 팀원 누구나 설치해서 쓸 수 있게 됨 ([진행 중](https://<사이트>/browse/AIP-3587), 리뷰 대기)
```

- 근거 티켓이 **하나면** 그 티켓에 건다.
- **여럿이면 대표 티켓 하나**에만 건다. 월요일은 거기서 끝이고, 수요일이면 나머지 티켓을 하위 항목 문장에 각각 건다.
- 근거가 **티켓 없이** 커밋·PR·Slack 댓글뿐이면 링크하지 않고 상태 텍스트만 쓴다. PR 링크로 대신하지 않는다 — 회의 페이지는 팀 밖에서도 읽는다.
- `jira` 설정이 `null` 이면 전부 링크 없이 쓴다.

**지라 티켓 번호(`AIP-1234`)를 글자로 쓰지 않는다.** 회의 페이지 맨 아래 `# 참고` 의 티켓 표가 이미 번호를 담고 있고, 번호는 읽는 사람에게 아무것도 알려주지 않는다. 2단계에서 **수집 목록을 보여줄 때는 번호를 그대로 쓴다** — 그건 사용자가 무엇인지 알아보라고 띄우는 화면이다. 번호가 빠지는 건 페이지에 들어가는 본문뿐이다.

```markdown
← 좋음
1. 관리자가 메일·문자 설정이 실제로 동작하는지 백오피스에서 바로 확인할 수 있게 됨 ([완료](https://<사이트>/browse/AIP-3212))

← 나쁨
1. 백오피스에서 메일,문자 발송 테스트 컴포넌트 및 기능 추가 개발 (AIP-3212, 완료)
```

선택한 항목이 5개보다 많으면 묶을 수 있는 것을 제안하고, 그래도 넘으면 무엇을 뺄지 묻는다. 수요일에는 월요일 공유 항목을 빼는 대신 묶는다. 월요일인데 5개가 안 되면 그대로 둔다. 개수를 채우려고 쪼개지 않는다.

#### 최상위 항목에 무엇을 쓸지 고르는 순서

위에서부터 해당하는 첫 번째를 쓴다.

**1. 제품이 달라지는 점이 있으면** 그걸 쓴다. 기본 경로다.

**2. 제품은 그대로인데 다른 기대효과가 있으면** 그 기대효과를 쓴다. 리팩터링, 빌드 시간 단축, 테스트 정비, 문서화, 운영 자동화처럼 고객에게는 안 보이지만 팀에 돌아오는 작업이 여기 해당한다. **무엇이 얼마나 나아지는지**를 쓴다.

```markdown
1. 배포 때마다 손으로 하던 이미지 태깅을 자동화해서 배포 1회당 10분쯤 줄어듦
    1. CI에 태그 생성 단계 추가
2. 알림 코드 중복을 정리해서 앞으로 알림 종류 추가가 쉬워짐
    1. 템플릿 처리 로직을 한 곳으로 모음
```

"리팩터링함", "코드 정리함" 같은 작업 이름만 적지 않는다. 그건 하위 항목에 갈 내용이다.

**3. 둘 다 판단이 안 서면 사용자에게 묻는다.** 그럴듯하게 지어내지 않는다.

> "AIP-1240은 제품에서 달라지는 게 있나요? 없다면 팀에 돌아오는 기대효과라도 있을까요? 최상위 항목에 쓸 한 줄이 필요합니다."

**4. 사용자도 모르겠다고 하면 모른다고 그대로 쓴다.** 추측해서 채우지 않고, 다시 캐묻지도 않는다.

```markdown
1. 프로덕트에 어떤 영향을 주는 작업인지 모르겠음 (완료)
    1. 알림 템플릿 로케일 폴백 수정
```

이건 미완성이 아니라 정상적인 출력이다. 회의에서 물어볼 지점이 명시된 상태이고, 그 자리에서 답을 얻으면 된다. 모른다고 적는 것을 망설이게 만들지 않는다. (월요일이면 하위 항목 대신 괄호로 붙인다.)

정리가 끝나면 사용자의 컨펌을 받는다.

### 5. 마크다운으로 검토 요청

최종 형태를 마크다운으로 출력해 검토를 요청한다.

**보내기 전에 스스로 읽기 수준을 점검한다.** 기준은 **컴퓨터공학 학사 수준에 쿠버네티스와 ML을 얕게 아는 사람**이다. 그 사람이 읽고 막히는 용어가 많거나 문장이 이해하기 어려우면, **순화한 뒤 순화한 내용으로 검토를 요청한다.**

순화했으면 그 사실을 한 줄로 알린다.

> "기술 용어가 많아 보여서 몇 군데 풀어 썼습니다. 의미가 달라진 데가 있으면 알려주세요."

**분량도 점검한다.** 항목 하나를 말로 설명하는 데 2분 안팎이 걸릴 분량인지 본다. 수요일이면 전체가 10~20분 안에 끝나는지 본다. 넘치면 하위 항목을 줄이거나 요약하는 안을 함께 제시한다. 어느 쪽이든 **사용자 검토를 거쳐 반영한다.**

### 6. 시각화 검토 (수요일)

수요일 회의는 발표자 PC를 화면에 연결해 리뷰한다. 승인된 항목, 특히 3단계에서 고른 **중점 항목** 가운데 **글보다 표나 그림이 빠른 것**이 있는지 검토한다.

- 표가 나은 경우: 이전/이후 비교, 여러 대상의 값·상태 비교, 선택지 비교
- 다이어그램이 나은 경우: 요청·데이터가 여러 컴포넌트를 거치는 흐름, 구조 변경, 상태 전이

해당하는 항목이 없으면 이 단계를 건너뛴다. 있으면 **어느 항목에 무엇을 그릴지 한 줄씩 제안**하고, 사용자가 고른 것만 만든다.

#### 어떤 형태로 만드나

**규모로 가른다.** 위에서부터 해당하는 첫 번째를 쓰고, 애매하면 사용자에게 묻는다.

1. **한 화면에 들어가는 단순 비교**(이전/이후, 값 몇 개, 선택지 몇 개) → 본문 **표**
2. **한 화면에 들어가는 흐름·구조** → 코드 블록 **텍스트 다이어그램**
3. **한 번에 표현되지 않거나 규모가 큰 것** → **Artifact**

3번은 이런 경우다 — 단계가 많아 코드 블록 하나에 안 들어가는 흐름, 여러 장면으로 나눠야 보이는 구조 변경, 표가 여러 개 필요한 비교, 색·위치·강조가 의미를 갖는 그림. **글자로 욱여넣지 말고 Artifact 로 만든다.**

Artifact 로 만들 때는:

- **조직 내부 공개로 게시한다.** 사외 공개로 만들지 않는다.
- 회의 페이지에는 그림을 다시 그리지 않고, **해당 항목의 하위 항목에 링크 한 줄**을 넣는다.
  ```markdown
  2. 워크로드 생성 요청이 거치는 경로가 한 장으로 정리됨 ([완료](…/browse/AIP-0000))
      1. 전체 흐름은 [구성도](<artifact 링크>)에서 볼 수 있음
  ```
- Artifact 도구를 쓸 수 없으면 SVG 로 만들고 파일 경로를 알려 사용자가 직접 첨부하게 한다.

형태를 정했으면 **만들기 전에 사용자에게 한 줄로 알린다.**

> "흐름이 7단계라 코드 블록에 안 들어갑니다. Artifact 로 만들어 링크를 걸까요?"

| 형태 | 만드는 법 | Confluence 반영 |
| --- | --- | --- |
| **표** | 본문에 마크다운 표로 쓴다. 별도 파일을 만들지 않는다 | 아래 배치 규칙을 따른다 |
| **텍스트 다이어그램** | 코드 블록 안에 아스키로 그린다. 별도 파일을 만들지 않는다 | 아래 배치 규칙을 따른다 |
| **SVG** | 작업 디렉토리에 `.svg` 파일로 만든다. 텍스트는 한글 그대로 두고 밝은 배경 기준으로 그린다 | 커넥터로 첨부할 수 없으면 파일 경로를 알려주고 사용자가 직접 첨부하게 한다 |
| **Artifact** | Artifact 도구가 있으면 공유용 페이지로 게시한다 | 해당 항목의 하위 항목으로 링크를 넣는다 |

만든 시각화도 검토를 받은 뒤 다음 단계에서 함께 반영한다.

#### 시각화를 어디에 두나

**그 항목에 붙인다.** 목록 맨 아래에 몰아 두지 않는다. 형태마다 넣는 자리가 다르다.

| 형태 | 자리 |
| --- | --- |
| **코드 블록** (텍스트 다이어그램) | 해당 항목 **안에** 들여쓰기로 넣는다. 하위 항목보다 먼저 온다 |
| **표** | 해당 항목(하위 항목까지)이 끝난 **바로 다음에**, 목록을 끊고 넣는다 |
| **Artifact · SVG** | 해당 항목의 **하위 항목에 링크 한 줄**. 본문에 그림을 옮겨 그리지 않는다 |

목록을 끊어도 **다음 항목 번호는 이어진다** — Confluence 가 `<ol start="N">` 으로 저장한다. 번호가 1부터 다시 시작할까 봐 표를 맨 아래로 밀지 않는다.

> ⚠ **표를 목록 항목 안에 들여쓰기로 넣지 않는다.** Confluence 가 `legacy-content` 블록으로 감싸고, 새 에디터에서 편집할 수 없는 덩어리가 된다(저장 사유: *"A table in list item can't be created or edited in the new editor"*). 회의 페이지는 매주 사람이 손대는 문서라 편집이 막히면 안 된다.

표나 다이어그램 아래에는 **무엇을 보라는 것인지 한두 줄**을 붙인다. 그림만 두고 넘어가지 않는다.

```markdown
1. 관리자가 화면에서 알림 임계값을 5단계로 고칠 수 있게 됨 ([완료](…/browse/AIP-3477))
    1. "긴급" 등급 값을 화면·API 모두 ALERT 에서 URGENT 로 바꿈

| 심각도 | 바꾸기 전 | 바꾼 뒤 |
| --- | --- | --- |
| 4 | 긴급 **ALERT** | 긴급 **URGENT** |

4단계만 바뀜. `ALERT` 가 "알림 기능" 자체를 가리키는 말과 겹치던 것을 정리함.

2. 다음 항목 — 번호는 2로 이어진다
```

### 7. Confluence 반영

사용자가 승인한 뒤에만 실행한다.

**해당 회의 페이지가 있으면** — 본인 `### 이름` 섹션의 내용만 교체한다.

**없으면** — 새로 만든다.

- 상위 페이지: 해당 월의 `스크럼 YYYY-MM` 페이지
- 제목: `YYYY/MM/DD : N주차` (진행 전이면 뒤에 ` (초안)`). 날짜는 회의 날짜, N은 ISO 주차
- 본문: **직전 회의 문서의 구조를 그대로 복사한다.** 섹션 구성과 팀원 이름 목록을 직전 문서에서 가져오고, 본인 외 섹션은 `- ..` 상태로 비워 둔다. 팀원 이름을 이 스킬에 적힌 것으로 채우지 말고 항상 직전 문서에서 읽어 온다. 직전 문서 상단의 회의 안건과 `# 참고` 의 티켓 표는 복사하지 않는다.

#### 다른 사람 영역을 건드리지 않는 법

페이지 갱신은 본문 전체를 덮어쓰는 방식이다. 반드시 이 순서를 지킨다.

1. 현재 페이지 본문을 읽어 온다
2. **`## 업무 공유` 아래의 본인 `### 이름` 블록만** 새 내용으로 바꾼다. 페이지 맨 아래 `# 참고` 의 티켓 표에도 같은 이름의 헤딩(`### 이름 (N건 / SP)`)이 있으니 그쪽을 고치지 않는다
3. 나머지는 읽어 온 그대로 둔다 — 공백, 줄바꿈, 빈 불릿 `- ..` 까지 포함해서
4. 갱신 후 다른 섹션이 그대로인지 확인한다

본인 이름은 Atlassian 계정 정보에서 확인하고, 확실하지 않으면 한 번 묻는다.

반영이 끝나면 페이지 링크를 알려준다.

## 페이지 형식

```markdown
# 이번주

## 업무 공유

### <팀원 이름>

- ..

### <본인 이름>

1. <결과> (완료 | 진행 중 | 할 예정)
    1. <과정>
2. <결과> (완료 | 진행 중 | 할 예정)
    1. <과정>

## 설치 & 교육

- ..

## 리서치 공유

- ..

## 주요 공유

- ..
```

회의에서 물어볼 것이 있으면 최상위 항목에 `[Q]` 를 붙인다.

```markdown
1. [Q] Workspace 접근제어에서 사용 시작 ~ 종료 로그를 어떻게 남길 수 있는지?
```

## 말투

기존 회의 문서와 같은 톤을 유지한다. 두 가지를 지킨다.

**첫째, 간결체로 쓴다.** 전체 문장이 아니라 `-음`, `-함`으로 끝낸다.

- `워크스페이스 접근 기록이 남도록 만들었습니다` → `워크스페이스 접근 기록이 남도록 함`
- `다음 주에 배포할 예정입니다` → `다음 주 배포 예정`

**둘째, 기술 용어가 문장 맨 앞에 오면 뒤로 보낸다.** 제품 언어를 앞에, 용어는 괄호에.

- `Istio PeerAuthentication을 STRICT로 변경함`
- → `서버끼리 주고받는 통신을 전부 암호화하도록 변경함 (Istio mTLS STRICT)`

용어를 지우라는 뜻이 아니다. 순서만 바꾼다.
